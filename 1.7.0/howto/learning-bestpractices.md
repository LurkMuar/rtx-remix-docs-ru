# Рекомендуемые практики

## Выбор подходящего формата USD

USD поддерживает несколько форматов: USD (двоичный), USDA (ASCII) и USDC. USD — двоичный формат, а USDA —
человекочитаемый текстовый формат ASCII.

Благодаря читаемости USDA удобно редактировать во внешних программах, что полезно при устранении проблем с ассетами и
при совместной работе.

Форматы USD загружаются немного эффективнее. Для распространения мода можно сконвертировать файлы USDA в USD, чтобы
ускорить загрузку.

## Организация захватов

В крупных проектах модов может понадобиться множество захватов, чтобы охватить все нужные изменения. Чтобы не терять в
них порядок, рекомендуется придерживаться единого правила именования, например добавлять к имени префикс раздела игры,
к которому относится захват. Так, захваты из первой главы можно называть с префиксом «ch1_».

```{warning}
Переименовывать захваты лучше до создания проекта в RTX Remix. Переименование захвата, который уже используется в
проекте, может привести к ошибкам при загрузке проекта. Переименовывать можно, только если на захват не ссылается ни
один существующий проект.
```

## Организация проекта с помощью слоёв

При создании мода основным целевым слоем служит файл `mod.usda`. Именно его читает рантайм.

По мере роста мода файл `mod.usda` может стать очень большим — тысячи или даже десятки тысяч строк.

Все переопределения можно поместить в слой `mod.usda`, но композиция слоёв помогает навести порядок.

Прежде чем делать замены, продумайте, с какими типами ассетов придётся работать. Разумно разнести замены по отдельным
слоям, например для замен моделей и замен материалов. Для больших игр может быть полезно также разделить слои по главам.

Переусердствовать с организацией можно, но разделение мода на слои-компоненты упрощает отслеживание изменений в долгой
перспективе.

Слои также полезны при командной работе. О настройке проекта для командной работы см. раздел
[Работа в команде](#работа-в-команде).

## Работа в команде

Ремастер игры может оказаться большой задачей, требующей работы целой команды. Поскольку моды Remix ориентированы
прежде всего на графику, полезно выстроить процесс так, чтобы художники могли эффективно работать вместе, даже если
меняется и игровая механика.

Если поручить настройку Remix и подготовку ассетов одному-двум людям, проще сохранять единообразие и избегать путаницы.
Если этими задачами занимается слишком много людей, в файлах проекта могут появиться ошибки и несоответствия.

Для отслеживания изменений и синхронизации команды настоятельно рекомендуется использовать системы контроля версий
(например, Git). Сведения о контроле версий ассетов см. в разделе
[Настройка контроля версий для проекта](#настройка-контроля-версий-для-проекта).

## Настройка контроля версий для проекта

Контроль версий — ценный инструмент для отслеживания изменений проекта: он позволяет вернуться к предыдущим версиям и
предотвращает потерю данных, особенно при командной работе.

Настраивая контроль версий, учитывайте следующее:

* Проекты Remix в основном состоят из художественных ассетов, поэтому подойдут системы контроля версий, оптимизированные
  для больших двоичных файлов, например Git LFS (Large File Storage) или Perforce.
* Настройте систему контроля версий так, чтобы она игнорировала файлы, создаваемые Remix (например, миниатюры), и
  репозиторий оставался чистым.
* Используйте стратегию ветвления для разных функций или изменений, чтобы работать параллельно, не мешая друг другу.

```{important}
Исключите из контроля версий папку `deps`: это символическая ссылка на папку rtx-remix игры, и переносить её между
системами нельзя.

Если не исключить эту папку, при попытке загрузить проект на другой системе могут возникать ошибки.
```

Добавление захватов в систему контроля версий упрощает обмен проектом. Однако захваты могут быть очень большими, и
тогда разумно хранить их отдельно, а под контролем версий держать только сам мод.

```{important}
Учтите, что распространение захваченных ассетов может нарушать условия использования игры, которую вы модифицируете.
```

## Выбор каталогов проекта

Рекомендуется создать для всех проектов RTX Remix отдельную папку *вне* каталога установки игры.

Например, если игра установлена в `C:/Program Files (x86)/Steam/common/Portal`, проекты можно создавать в
`C:/Users/<USER>/RemixProjects` или `D:/RemixProjects`.

## Относительные пути для переносимости

Абсолютные пути поддерживаются, но для переносимости рекомендуется использовать относительные. Тогда проект можно
переносить на другие системы без исправления путей.

При создании проекта RTX Remix Toolkit создаёт структуру папок, включающую символическую ссылку `deps`. Она связывает
проект с папкой игры `rtx-remix/mod`, и именно её следует использовать при ссылках на захваты или сторонние
моды-зависимости.

```{tip}
**Пример**

Вместо абсолютного пути к захвату:

`C:\Program Files (x86)\Steam\common\Portal\rtx-remix\captures\capture_01.usd`

используйте относительную переносимую ссылку:

`./deps/captures/capture_01.usd`.
```

## Исходные и импортированные ассеты

Для порядка можно создать в папке проекта дополнительные папки, чтобы разделить исходные и импортированные ассеты. Такая
структура особенно полезна для проектов под контролем версий: в ней легко отслеживать изменения как исходных, так и
импортированных ассетов.

* Исходный каталог:
    * Содержит ассеты и текстуры до импорта (FBX, USD, OBJ и т. д.).
    * Может находиться вне каталога проекта.

* Выходной каталог:
    * Создаётся вручную внутри каталога проекта.
        * Подходящий выходной каталог — `(project_root)/assets/ingested/`.
    * Функция копирования внешних ассетов по умолчанию использует `(project_root)/assets/ingested/`.
    * Содержит импортированные ассеты (USD или DDS), на которые ссылается проект.

### Подключение внешнего хранилища ассетов

Поскольку папки проектов и исходных ассетов могут быть большими, можно хранить ассеты в центральном хранилище и
подключать их к проектам через символические ссылки.

Пример команды:

```bat
mklink /J "YOUR_PROJECT_DIR/assets" "INGESTED_ASSET_DIR"
```

## Снижение шума при переосвещении

Большое количество источников света может увеличить шум из-за неэффективности сэмплирования источников при рендеринге.
Аналогично шум могут вызывать многочисленные перекрытые источники света на небольшом участке. В тесных помещениях это
обычно допустимо, но на больших пространствах может стать проблемой.

С другой стороны, недостаточное освещение участка тоже может усилить шум, поскольку рендереру приходится опираться на
более длинные световые пути. Это бывает неизбежно в местах, освещённых в основном непрямым светом.

Тонкая геометрия или детализированная кривизна на отражающих или прозрачных поверхностях могут вносить шум: дрожание
камеры (camera jitter), используемое для сглаживания и апскейла, может мешать шумоподавителю, поскольку Remix теряет
возможность отслеживать геометрию между кадрами.

Не допускайте пересечения источников света с другой геометрией: это снижает эффективность сэмплирования.
